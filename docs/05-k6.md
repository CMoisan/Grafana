# 05 — k6 : tests de charge et simulation d'usage

**k6** est l'outil de test de charge racheté par Grafana Labs en 2021. Écrit en
Go, scripté en JavaScript, il s'intègre nativement à Prometheus/Mimir et à
Grafana. C'est la brique « tests » de la plateforme Grafana, aux côtés de Grafana
Cloud k6 (l'offre managée avec exécution distribuée).

> **Ce n'est pas Node.js.** Chaque VU (*utilisateur virtuel*) est une goroutine
> exécutant une VM JavaScript isolée. Pas de `npm`, pas de `require()`, pas de
> `setTimeout`, pas d'accès disque à l'exécution. Uniquement des imports ES6 et
> les modules `k6/*`.

---

## Les 5 types de tests

| Type | Durée | Charge | Ce qu'il détecte |
|---|---|---|---|
| **Smoke** | 1 min | 1 VU | le système fonctionne-t-il ? |
| **Load** | 5–30 min | charge nominale | tient-on l'objectif de service ? |
| **Stress** | 10–30 min | croissante | où et **comment** ça casse |
| **Soak** | 4–24 h | modérée | fuites mémoire, dégradation lente |
| **Spike** | 5 min | brutale | résistance à un pic (Black Friday) |

**L'erreur la plus répandue** : ne faire que des load tests. Un load test valide
un objectif ; il ne dit ni où est la limite, ni si le système fuit.

---

## Executors : le choix qui change tout

C'est **la** notion technique de k6 à maîtriser.

### `constant-vus` / `ramping-vus` — piloté par les utilisateurs

N VUs qui bouclent en continu. **Le débit dépend du temps de réponse.**

Conséquence : si le système ralentit, les VUs attendent, le débit baisse
tout seul et le test **masque** la dégradation. C'est le phénomène de
*coordinated omission*.

### `constant-arrival-rate` / `ramping-arrival-rate` — piloté par le débit

k6 maintient N itérations par seconde **quoi qu'il arrive**, en ajoutant des
VUs si nécessaire.

C'est le comportement réel des utilisateurs : ils ne ralentissent pas parce que
votre serveur souffre. **Utilisez cet exécuteur par défaut.**

Si k6 affiche *« insufficient VUs »*, c'est déjà un résultat : le système ne
tient pas le débit demandé.

### Les autres

- `shared-iterations` / `per-vu-iterations` : nombre fixe d'itérations. Utile
  pour les scénarios ponctuels — c'est ce qu'utilise l'injecteur de panne du
  script de simulation.
- `externally-controlled` : piloté par l'API pendant l'exécution.

## Thresholds : transformer un test en garde-fou

```javascript
thresholds: {
  http_req_duration: ['p(95)<500', 'p(99)<1500'],
  http_req_failed: ['rate<0.01'],
  checks: ['rate>0.99'],
  'http_req_duration{scenario_type:lecture}': ['p(95)<200'],  // par tag
}
```

Un seuil non respecté → **k6 sort avec le code 99** → le pipeline CI échoue.

**Sans thresholds, un test de charge n'est qu'une jolie image que personne ne
regarde.** C'est le conseil le plus rentable à donner à une équipe qui débute.

## Métriques intégrées

| Métrique | Signification |
|---|---|
| `http_req_duration` | **la** métrique principale : durée totale |
| `http_req_waiting` | TTFB : le temps de traitement serveur |
| `http_req_connecting` | établissement TCP |
| `http_req_tls_handshaking` | négociation TLS |
| `http_req_failed` | taux d'échec (redéfinissable, voir plus bas) |
| `iteration_duration` | durée d'un parcours complet, `sleep` inclus |
| `vus` / `vus_max` | VUs actifs / alloués |
| `dropped_iterations` | itérations non exécutées faute de VUs — **à surveiller** |

**Décomposition utile en diagnostic** :
`http_req_duration` = `connecting` + `tls` + `sending` + `waiting` + `receiving`.

Si `waiting` domine → le serveur est lent.
Si `connecting` domine → problème réseau, DNS ou saturation du pool de connexions.

## Le piège des codes 4xx attendus

Par défaut, k6 compte toute réponse ≥ 400 comme un échec. Un test qui vérifie
volontairement un 404 fera donc échouer `http_req_failed: ['rate==0']`.

```javascript
http.setResponseCallback(
  http.expectedStatuses({ min: 200, max: 399 }, 404, 409)
);
```

C'est exactement le même raisonnement que côté Prometheus : distinguer *faute du
client* et *panne du service*. Sans cela, vos tests deviennent instables et
l'équipe finit par les ignorer.

## Exporter vers Mimir : la vue client + la vue serveur

```bash
k6 run --out experimental-prometheus-rw script.js
# avec K6_PROMETHEUS_RW_SERVER_URL=http://mimir:8080/api/v1/push
```

Les métriques k6 arrivent dans Mimir préfixées `k6_`, et vous pouvez alors les
superposer aux métriques applicatives **dans le même graphe** :

```promql
# Vue CLIENT : ce que l'utilisateur subit
k6_http_req_duration_p95

# Vue SERVEUR : ce que l'application mesure
histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket[5m])))
```

**L'écart entre les deux courbes est la donnée la plus précieuse du test.** Il
contient le réseau, l'ingress, la file d'attente TCP et l'attente d'un thread
disponible — tout ce qui se passe **avant** que votre code ne démarre.

Beaucoup d'équipes ne regardent que la vue serveur, concluent « tout va bien »,
pendant que les utilisateurs attendent deux secondes. Savoir montrer cet écart
en démo est très marquant.

## Interpréter un stress test

Ordre d'apparition des symptômes, systématiquement observé dans ce lab :

1. **`http_req_waiting` p99 décroche** — saturation du pool de threads Tomcat
   (200 par défaut). Les requêtes attendent avant d'être traitées.
2. **`container_cpu_cfs_throttled_seconds_total` > 0** — la limite CPU du pod
   est atteinte, le noyau ralentit le conteneur. Cause de latence la plus
   sous-diagnostiquée sur Kubernetes.
3. **`jvm_gc_pause_seconds` monte** — pression mémoire, le GC vole du CPU.
4. **Les erreurs apparaissent, en dernier.**

**La conclusion opérationnelle** : alertez sur la latence (signal précoce), pas
seulement sur les erreurs (signal tardif). Quand les erreurs arrivent, vos
utilisateurs souffrent depuis plusieurs minutes.

## À savoir sur l'écosystème k6

- **Extensions (xk6)** : k6 se recompile avec des modules (Kafka, SQL, gRPC,
  Redis, navigateur…). Argument face à un client qui teste autre chose que HTTP.
- **k6 browser** : automatisation Chromium intégrée, pour mesurer les **Core Web
  Vitals** (LCP, CLS) en plus des métriques serveur.
- **Grafana Cloud k6** : exécution distribuée depuis plusieurs régions,
  historique des runs, comparaison entre versions. C'est l'offre commerciale
  au-dessus de l'outil open source.
- **Positionnement** : k6 remplace JMeter et Gatling avec un scriptage moderne,
  une empreinte mémoire bien plus faible, et surtout une intégration native à
  Grafana. Sachez le formuler en une phrase.
